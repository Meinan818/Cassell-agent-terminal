# Source 03 — Official Claude Code Docs: Agent Teams
URL: https://code.claude.com/docs/en/agent-teams
Read: 2026-11-12, verified live via browser_open (updated 2026-11-10T02:50:27Z per footer)
Status: OFFICIAL / PRIMARY — but DISTINCT from ultracode/dynamic workflows; do not conflate.

Key facts:
- "Agent teams let you coordinate multiple Claude Code instances working together. One session acts as the team lead, coordinating work, assigning tasks, and synthesizing results. Teammates work independently, each in its own context window, and communicate directly with each other. You can also talk to any teammate directly without going through the lead."
- Best for: research/review (investigate different aspects simultaneously, then share and challenge each other's findings), new modules/features each owning separate piece, debugging with competing hypotheses (test different theories in parallel, converge faster), cross-layer coordination (frontend/backend/tests owned by different teammate).
- "Agent teams add coordination overhead and use significantly more tokens than a single session. They work best when teammates can operate independently. For sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective."
- Comparison subagents vs teams: Subagents own context, return result to caller, main agent manages all work, lower token cost (results summarized back), best for focused tasks where only result matters. Teams: own context, fully independent, teammates message each other directly, self-coordination via messages + shared task list, higher token cost (each teammate separate Claude instance), best for complex work requiring discussion/collaboration. "Use subagents when you need quick, focused workers that report back. Use agent teams when teammates need to share findings, challenge each other, and coordinate on their own."
- Enable: disabled by default, CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 in shell or settings.json. Enabling changes ordinary delegation: Claude may name a subagent on its own, and while enabled a named subagent launches as teammate, so teams can form even when you didn't ask. Spawning teammates requires interactive session; in -p / Agent SDK, named subagent runs as ordinary subagent.
- Introduced: v2.1.32 (2026-02-05) as research preview alongside Opus 4.6 — corroborated by secondary sources and Anthropic Opus 4.6 announcement snippet in search (see notes/source-07). Official docs page itself does not state date in extracted text; treat date as secondary-corroborated.
- Start: describe task + teammates in natural language; Claude spawns them. Lead populates shared task list in session that has Task tools, spawns teammates per perspective, explores, synthesizes when finished. Claude may sometimes use subagents instead; panel alone doesn't confirm team formed.
- Control/display: in-process (all teammates inside main terminal, arrow keys select, Enter view/message, x stop, Ctrl+T task list) vs split panes (each teammate own pane, requires tmux or iTerm2 + it2 CLI). Default in-process; teammateMode in ~/.claude/settings.json, --teammate-mode flag experimental. Idle rows hide after 30s when all idle, reappear on next turn; >3 idle collapse into "N idle agents".
- Models per teammate: 1) model named in spawn prompt, 2) subagent definition model (inherit = lead's), 3) CLAUDE_CODE_SUBAGENT_MODEL if not inherit, 4) lead's current model. Org availableModels allowlist substitution rules. Teammate on lead's model inherits lead's effort level.
- Plan before implementing: teammate spawned while lead in plan mode also works in plan mode until plan ready; sends plan approval to lead; if permission mode unchanged, Claude Code approves as soon as request arrives without lead reviewing; if put in plan mode via Shift+Tab while viewing, lead reviews instead.
- Talk directly: each teammate full independent session; message directly, give instructions, redirect.
- Tasks: shared task list, pending/in progress/completed, dependencies show blocked until dependencies completed, teammates don't self-claim blocked task, lead assigns or self-claim after finishing; claiming uses file locking to prevent race conditions.
- Shutdown: refer by name, lead sends shutdown request, teammate can approve (graceful exit) or reject with explanation; shared dirs cleaned up automatically when session ends.
- Quality gates hooks: TeammateIdle (exit 2 sends feedback, keep working), TaskCreated (exit 2 prevents creation + feedback), TaskCompleted (exit 2 prevents completion + feedback).
- Architecture: components lead / teammates / task list / mailbox. Mailbox is JSON file ~/.claude/teams/{team-name}/inboxes/{agent-name}.json; Claude Code validates every entry, invalid entries reported as errors and removed, valid still delivered; reported as sent only when write succeeds; write failure => sending agent receives error, nothing sent. Task dependencies auto-unblocked on completion. Team config ~/.claude/teams/{team-name}/config.json removed when session ends; task list ~/.claude/tasks/{team-name}/ stays on disk (cleanupPeriodDays).
- Subagent definitions for teammates: tools list limits teammate (+SendMessage in-process, +TaskCreate/TaskGet/TaskList/TaskUpdate if Task tools session), model, disallowedTools, effort, autoCompactWindow (v2.1.296+ in-process), body appended to default system prompt in-process / replaces it split-pane, skills NOT applied, mcpServers split-pane only.
- Permissions: cycle teammate permission mode Shift+Tab; can't set per-teammate at spawn; new teammate starts with lead's mode incl bypassPermissions; lead in dontAsk => teammate starts Manual. In-process teammate runs under lead's live allow/deny rules. Teammate permission prompts appear in lead session. Messages between agents: receiving agent told message came from another Claude session not user; teammate can't approve permission prompt or supply consent on your behalf, denied action can't be relayed to bypass; auto mode classifier treats approval claim relayed from another agent as untrusted, reviews each message before delivery, blocked message never reaches recipient.
- Context/communication: each teammate own context; loads same project context CLAUDE.md, MCP, skills; does NOT inherit lead conversation history; spawn prompt only. Automatic message delivery (lead doesn't poll), idle notifications (finishes => notifies lead incl final answer; API error => notifies lead incl error text), shared task list, teammate messaging by name (one message per recipient to reach everyone).
- Token usage: significantly more than single session, scales with number teammates; in-process cache 5 min default, subagentPromptCacheTtl 1h.
- Use cases detail: parallel code review (security/perf/test coverage lenses, lead synthesizes), competing hypotheses (explicitly adversarial, each challenges others; debate fights anchoring).
- Best practices: give enough context (no lead history), team size 3-5 recommended, no hard limit but token linear, coordination overhead, diminishing returns; size tasks self-contained deliverable; wait for teammates (lead may start implementing itself instead — tell it to keep going / wait); start with research/review; avoid file conflicts (same file edits => overwrites, each owns different files); monitor/steer, don't leave unattended too long.
- Troubleshooting/limits: No session resumption with in-process teammates (/resume and /rewind do not restore them); task status can lag (teammates fail to mark completed, blocks dependents — update manually / nudge); shutdown can be slow; one team per session; no nested teams; no background subagents from in-process teammates; lead fixed for lifetime; no per-teammate permission modes at spawn; split panes require tmux/iTerm2, not supported in VS Code integrated terminal, Windows Terminal, Ghostty. Teammates may stop after errors instead of recovering; lead can stop early deciding team finished before tasks complete.

# 抄什么、不抄什么：Claude、Codex、天枢

> 研究日期：2026-11-13 · 重新调研（2026-11-12 的旧报告全部复核过，结论见 §6）
> 一句话背景：卡塞尔专员终端要对标这三家的**功能完整度**，长相绝不照抄。NORMA=办公（对标 Claude Cowork），EVA=工程（对标 Claude Code）。
> 写法说明：用户是代码新手，本文尽量说大白话；出现术语第一次出现时会解释。每个判断都写了"为什么"，不确定的写"未证实"，不编造。
>
> **总原则（用户 2026-11-13 亲口定）：三家都保持质疑，一个都不盲信。** 天枢是年轻一代、小作坊，它的功能再亮眼也不能盲目相信、盲目听从——要先推理"这东西可不可行、对卡塞尔合不合适"，想通了才抄。Codex 和 Claude 是大厂，但也一样要质疑：大厂的方案也有自己的前提（账号体系、云端、规模），照搬过来未必成立。本文每一处"抄"的判断，都按这个标准过了一遍；以后再补新功能，也先按这个标准推理一遍。

## §0 一句话结论

| 产品 | 最值得抄的一点 | 绝对不要抄的一点 |
|---|---|---|
| **Claude** | **Cowork 的"文件夹级授权 + 删除永远要批"**：让用户敢把文件交给它，是办公 agent 能用的前提 | **不要抄"品牌先分后合"的折腾**：Cowork 独立品牌只活了 8 个月就被合并，名字最终会消失；卡塞尔一开始就要想清楚 NORMA/EVA 是长期分工 |
| **Codex** | **"沙箱 × 审批"两把独立 dial + Plan/Goal 工作流**：安全和"先定方案再锁定目标"是它最成熟的设计 | **不要抄"云端"**：Codex 的云任务、云端评审、手机遥控都依赖 OpenAI 的账号和服务器，BYOK 本地产品自建云端是死路 |
| **天枢** | **"前缀缓存优先"的整套省钱工程**：系统提示词冻结成固定前缀、动态内容只走增量，实测长会话命中率 99.3–99.6%、账单从 ¥880 降到 ¥20 | **不要抄星域的玄学包装**：北斗七星、碑文、创始记忆那套叙事和龙族语境不搭；只借"可切换工作纪律"的机制 |

## §1 Claude：Code、Cowork、Desktop

### 1.0 先弄清三者的关系

很多人把这三个名字搞混，先说清楚：

- **Claude Code**：给开发者的，写代码、跑测试、发版。形态有终端命令行、桌面端里的 Code 页签、网页版、手机版。
- **Claude Cowork**：给不写代码的知识工作者的，做办公活——写文档、做表格、做演示、整理文件、定时汇报。2026-01-12 上线，2026-04-09 正式发布，**2026-09-16 并入普通对话，不再是独立模式**，品牌最终会消失。
- **Claude Desktop**：桌面端应用。现在里面是两个顶层入口：统一后的对话（含 Cowork 能力）+ Code 页签。

**最关键的转折**：Anthropic 发现用户最烦的是"决定任务属于哪里"（"最烦决定任务属于哪里"是用户原话的转述），于是把 Chat 和 Cowork 合并，让 Claude 自己判断任务要快速回答还是多步骤代理；**只有 Code 保持独立**，因为写代码的权限模型（整机访问、跑终端）和办公（文件夹沙箱）根本不同，必须分开。

### 1.1 Claude Code：功能清单

| 能力 | 一句话说明 |
|---|---|
| 思考强度五档 | Low / Medium / High / XHigh / Max，管模型想多深；档位按模型保存，Max 只对当前会话有效 |
| Ultracode（动态工作流） | 一个开关：打开后，Claude 会自己给大任务写一段编排脚本，派几十到几百个子代理并行干活，最后汇总成一个答案；不是模型、不是档位。2026-05-28 上线，2026-09-28 起独立于思考强度 |
| 权限模式六档 | Manual（每步都问）/ Accept edits（改文件自动、跑命令问）/ Plan（只出方案不动文件）/ Auto（默认，后台分类器拦截高风险）/ dontAsk（会弹窗的一律拒绝）/ Bypass（全放行，仅容器里用） |
| 沙箱 | 只包住 shell 命令；默认关闭；macOS 用 Seatbelt、Linux 用 bubblewrap；原生 Windows 没有沙箱 |
| 子代理 | 派出去的工人，各自独立的上下文，干完只把摘要交回来；内置 Explore（只读侦察）、Plan（只读规划） |
| Agent Teams（实验性） | 一个主会话带几个平级会话，像一个小组：共享任务清单、互相发消息；和 ultracode 是两套不同的机制，不要混为一谈 |
| 检查点 / 倒带 | 每次改文件前先快照；随时可以回到之前某一步，只回对话、只回代码、或者两者都回；只管 Claude 自己改的文件，不管用户手改的和终端命令改的 |
| 计划模式 | 先调查、给方案、等用户批准再动手；方案可以打开编辑 |
| 技能 / MCP / 钩子 | 技能是 `SKILL.md` 文件夹做的可复用剧本；MCP 是接外部工具的标准；钩子是 33 个生命周期事件上挂的自动检查 |
| 会话管理 | 恢复、重命名、分支（fork）、清空、导出；桌面端侧栏列会话、支持分屏看两个会话、后台会话跑完有系统通知 |
| 云端会话与 Projects | 会话可以在 Anthropic 云端跑（关掉应用也继续）；Projects 是长期项目工作区（公开测试版） |
| 代码审查与 diff | 改动以 diff 形式展示，可逐行评论、接受/拒绝；桌面端有 Review code 按钮；`/code-review`、`--fix`、`--comment` |
| 电脑操作（研究预览） | 直接操作屏幕、点按应用；Pro/Max 可用，Team/Enterprise 不可用 |
| 定时任务 | `/schedule`，云端按节奏跑 |
| 远程控制 | 手机上继续桌面端的会话（Dispatch，Pro/Max） |

### 1.2 Claude Cowork：功能清单（旧报告里缺失，本次重点补齐）

| 能力 | 一句话说明 |
|---|---|
| 本地文件读写 | 只碰用户明确授权的文件夹，读/写/创建/整理，不用上传下载 |
| 交付真实成品 | 生成带可用公式的 Excel、能直接讲的 PPT、格式好的 Word，不是"怎么做"的教程 |
| 多步骤长任务 | 自己拆步骤、自己跑完；可同时跑多个任务；合上电脑云端继续跑（需要本地文件的任务除外） |
| 子代理并行 | 大项目拆成并行块（一个查竞品、一个画对比表） |
| 定时任务 | `/schedule`，日报/周报/收件箱摘要按节奏自动跑 |
| 连接器 / MCP | Google Drive、Gmail、Microsoft 365、Slack 等，任务中随时取数 |
| 联网与浏览器 | 内置浏览器开网站、填表；优先级是：连接器 > 浏览器 > 屏幕操作（最后手段） |
| Projects 工作区 | 相关任务分组，文件、指令、记忆跨会话保留 |
| 插件 | skills + 连接器 + 子代理 + 斜杠命令打包成一次安装，装完就像该岗位的专员 |
| Docs / Slides / Design | 对话内直接做可协作的文档、演示、品牌视觉（2026-09-16 上线，beta） |
| 文件夹级授权（核心） | 在用户明确连接文件夹之前，Cowork 看不到任何文件；只在授权范围内工作 |
| 三档审批 | Manual（每步都问）/ Auto（默认，自动安全审查、拦截危险动作）/ Skip（不问不查）；**删除文件永远要批**，所有模式都一样 |
| 电脑操作（研究预览） | 每访问一个应用都要单独许可；看得到在干什么、随时可叫停 |

**Cowork 不能做的事（官方明确划的线）：**
- 不做软件开发（那是 Code 的地盘）。
- 不要用它处理银行/投资、法律合同、医疗健康信息、敏感工作账号。
- 不要把它指向含凭证、财务文件、个人记录的文件夹。
- 提示注入风险官方承认"永远无法完全消除"——Cowork 会读用户信任边界之外的外部内容（网页、文档、邮件），里面可能藏恶意指令。
- 早期版本活动不进审计日志，不适合受监管工作（2026-11 企业安全更新后 Team/Enterprise 可经 OpenTelemetry 传到 SIEM，早期说法是否仍成立——**未证实**）。

### 1.3 Cowork 与 Code 的分工对照表

| 维度 | Cowork（→ NORMA） | Claude Code（→ EVA） |
|---|---|---|
| 面向谁 | 不开终端的知识工作者 | 开发者 |
| 任务 | 研究、分析、文档、表格/演示、整理文件、定时汇报 | 写代码、调试、跑测试、发版 |
| 文件范围 | **仅限授权文件夹**（沙箱） | **整台机器**，可跑终端命令 |
| 审批模式 | Manual / Auto（默认）/ Skip；删除永远要批 | Ask（默认，看 diff）/ Code / Plan / Auto |
| 产物 | 文档、表格、演示、研究报告 | 可运行的软件、PR |
| 形态命运 | 2026-09-16 **并入统一对话**，品牌将消失 | **保持独立页签**，未合并 |
| 共用什么 | 同一套 agentic 引擎、同一个模型、同一套 skills/插件格式、同一套审批哲学 | 同左 |

**切换的本质是权限边界不同（文件夹沙箱 vs 整机访问），不是功能多少。**

### 1.4 抄什么（Claude）

| # | 抄什么 | 为什么适合卡塞尔 |
|---|---|---|
| C1 | **文件夹级授权**：NORMA 在用户选文件夹之前看不到任何文件；授权以文件夹为单位；删除永远单独确认 | 用户最怕"AI 在我电脑上乱动"。把信任变成一次具体动作（选文件夹），而不是一句口号。卡塞尔是 BYOK 本地应用，没有云端沙箱，文件夹授权就是唯一的安全边界，更要做扎实 |
| C2 | **三档审批 + 消息框内的权限开关**：Manual / Auto / Skip 收在消息框一个开关里；默认 Auto；删除、发邮件、对外操作永远进确认 | 不同任务风险不同，用户不想每个任务都重新配置；同时保留一条"永远要批"的硬底线 |
| C3 | **先给计划、再动手；全过程透明**：接长任务先出计划卡（可改可批），执行中每步展示"开了哪些文件、用了哪些工具、做了什么选择"，随时可改向、可叫停 | 长任务最怕"黑盒"。这是卡塞尔现有 ThinkBlock/ToolCard 的直接升级方向 |
| C4 | **"说目标，不说步骤" + 子代理并行**：用户只说想要什么结果，Claude 自己拆解；大项目拆成并行块 | NORMA 的任务编排器就该这样：目标 → 计划 → 并行子任务 → 汇总成品；前端要让"并行"看得见（多路进度并排），而不是串行转圈 |
| C5 | **定时任务**：`/schedule`，把一次委托变成固定节奏（周报、收件箱摘要） | 办公 agent 的杀手级功能，优先级高于花哨功能；但要诚实说明本地版"关机跑不了" |
| C6 | **成品导向**：交付"能直接用的文件"，不是"怎么做"的文字；验收标准是"文件能不能直接交" | NORMA 的验收标准就该是这个；前端要给成品文件预览、下载、继续改的入口 |
| C7 | **检查点 / 倒带**：改文件前快照，可回对话、可回代码、可两者都回 | EVA 的"后悔药"，Claude 有、Codex 没有（见 §2），是抄 Claude 不抄 Codex 的关键区别 |
| C8 | **Ultracode 的编排原语**：LLM 写的编排脚本、`parallel()`（等全部完成）vs `pipeline()`（每件独立流过各阶段）、脚本变量存中间结果、对抗式审查/投票 | 这是 EVA 并行编排的正规军打法，比"写死 3 个智能体"高一个段位；详见 §4 的 ULTRACODE 一节 |
| C9 | **计划模式**：先调查、给方案、等批准再动手 | EVA 做大重构前的标准动作；Codex 也有，但 Claude 的 Plan 模式和权限模式是同一套体系，更干净 |
| C10 | **插件 = 专家打包**：skills + 连接器 + 子代理 + 斜杠命令，打包一次安装 | NORMA 的"工作方式"预设可以学这个形态：装一个"周报专家""报销专家"的包，里面含指令、工具权限与产出模板 |
| C11 | **工具优先级：连接器 > 浏览器 > 屏幕操作** | NORMA 的工具调用顺序应固定下来；屏幕操作如要做，必须单独授权、单独开关，默认关闭 |
| C12 | **不要让用户事前选模式（长期方向）**：一个输入框，模型按任务自动选边；只在"要碰整机/跑命令"时才明确切 EVA | Anthropic 走过"先分模式、再合并"的路，用户最烦"决定任务属于哪里"。NORMA/EVA 长期应走向这个方向 |

### 1.5 不抄什么（Claude）

| # | 不抄什么 | 为什么 |
|---|---|---|
| D1 | **"品牌先分后合"的折腾** | Cowork 独立品牌只活了 8 个月就被合并，名字"最终会消失"。卡塞尔一开始就想清楚 NORMA/EVA 是长期分工，不要先分后合 |
| D2 | **"合上电脑继续跑""手机接力"背后的云端** | 依赖 Anthropic 云端会话；卡塞尔本地架构做不到时不要在界面上暗示能做到。可以抄"异步任务"的产品形态（后台队列、离开再回来验收），不要假装有云端 |
| D3 | **电脑操作（computer use）的默认开启** | 仍是研究预览，且每次访问应用都要许可；卡塞尔现阶段不做屏幕操作，默认关闭 |
| D4 | **早期"无审计日志"的坑** | Cowork 早期因活动不进审计日志被排除在受监管工作之外；卡塞尔若面向办公用户，操作日志（谁、什么时候、动了哪个文件）应从第一天就有 |
| D5 | **Claude 的模型名与档位名硬编码** | 模型名漂移很快（Opus 5.5 / Sonnet 5.5 / Haiku 5.5 / Fable 5.2 是 2026-11-13 的版本）；BYOK 模型各有自己的档位，不要把 Claude 的档位名照搬到 DeepSeek 等模型上 |
| D6 | **Agent Teams 的整套机制** | 实验性、限制多（一个会话只能一个团队、不能嵌套、不能恢复）；ultracode 的工作流脚本已覆盖并行编排的主要场景，Teams 是另一条线，现阶段不抄 |

## §2 Codex：桌面端、CLI、云端

### 2.0 先弄清 Codex 是什么

一个名字、四种形态、同一套 agent：

1. **ChatGPT 桌面 App 里的 Codex 模式**（2026-07-09 原独立 Codex App 并入 ChatGPT 桌面 App；App 内 Chat / Work / Codex 三模式并列）。
2. **开源 Codex CLI**（Rust，Apache-2.0，`github.com/openai/codex`，最新稳定版 v0.167.2，2026-11-11）。
3. **IDE 扩展**（VS Code / Cursor / Windsurf，JetBrains 与 Xcode 为内置集成）。
4. **Codex Cloud / Web**（云端隔离环境跑任务、出 PR）+ 手机 Remote（ChatGPT 移动 App 遥控本机）。

**OpenAI 的分工和 Anthropic 趋同**：办公 = 主应用内的通用 agent（Work），工程 = 专门的 Codex；两家都没有把办公 agent 与工程 agent 合并。2026-11-04 OpenAI 宣布收购 Pierre Computer（Code Storage 代码托管 + Trees/Diffs 库），要把代码托管能力带进 Codex——Codex 正从"写代码的 agent"向"代码存放、理解、评审的基础设施"扩张（交易尚未交割）。

### 2.1 Codex：功能清单

| 能力 | 一句话说明 |
|---|---|
| 思考强度六档 | Low / Medium / High / XHigh / Max / Ultra；Ultra = Max 推理 + 自动派生并行子代理（官方原话确认）；Luna 最高到 Max、不支持 Ultra；桌面端 Ultra 藏在"设置 > 配置 > Ultra in model picker slider"开关后面 |
| 沙箱 × 审批：两把独立 dial | **沙箱**（技术上能碰什么：read-only 只读 / workspace-write 读写工作区、默认断网 / danger-full-access 无边界）；**审批**（何时停下问你：untrusted / on-request / never）。两把 dial 各自独立，不要合成一把 |
| 权限预设 | Auto（默认）= workspace-write + on-request；Read Only = read-only + on-request；Full Access = danger-full-access |
| 计划模式 / 目标模式 | `/plan` 先定路线（怎么做）、`/goal` 再锁定终点（做到什么算完）；官方推荐顺序就是先 plan 后 goal；Goal 是线程级持久目标，空闲时自动续跑、拿证据判定完成，≤4,000 字符 |
| 子代理 | 只在明确要求时派生（或 AGENTS.md / skill 指示）；内置 default / worker / explorer；自定义 agent 是 TOML 文件，可配模型与努力 |
| Worktree 并行隔离 | 新建聊天选 Local（当前目录）/ Worktree（隔离 Git worktree）/ Cloud（云环境）；Handoff 在 Local↔Worktree 间迁移聊天 |
| 审查队列 / Triage | 桌面端侧栏收自动化 + worktree 任务的结果，等用户批准/驳回；审查面板可按文件、按 chunk stage/revert，行间评论回传 |
| 定时任务 Automations | 左侧 Scheduled 页：Standalone（cron 式独立运行）与 Thread（附着在单个 thread 上的心跳唤醒）两种；结果进 Triage，没结果自动归档；本地任务要求电脑开着、App 在运行 |
| 技能 / 插件 / MCP / 钩子 | Skills 是 `SKILL.md` 目录包（渐进披露，先只加载名字和描述）；插件打包 skills + MCP + 应用；MCP 三端共享同一配置，支持 OAuth 登录；钩子 **14 个事件**（2026-11-13 官方确认，**支持 Windows**——旧报告"暂不支持 Windows"的说法已被证伪） |
| 会话管理 | 恢复、重命名、置顶、归档、删除、Fork（复制聊天为新 ID，Esc Esc 编辑上一条消息即 fork）；`/export` 存 Markdown、`/recap` 只摘要不压缩；**没有文件级 rewind**（文件回滚靠 git；GitHub 上要求加 `/rewind` 的 issue #11626 至今还是 open 的功能请求） |
| 云端任务与 ChatOps | 云端隔离环境跑任务、出 PR；Slack 里 `@ChatGPT`、Linear 里 `@Codex`、GitHub 上 `@codex review` 都能触发云任务 |
| 队列 / 改向（Queue / Steer） | 运行中发消息可选 Queue（等本轮结束）或 Steer（注入本轮改方向）；排队消息列在输入框上方，可编辑、重排、删除 |
| 桌面宠物 Pets | 浮在窗口之上、反映任务状态的小宠物：Running / Needs input / Ready / Blocked 四态；可自己做宠物（换外观、不改行为） |

## §3 天枢 TIANSHU

### 3.0 先弄清天枢是什么

天枢（huiliyi37/Tianshu-harness，Apache-2.0 开源）是一个 TypeScript 写的**编程 agent 运行时**：终端 TUI、桌面端（Tauri）、VS Code 插件共用同一个内核。它在模型与真实世界之间加了一层**认知执行环境 CVM**（Cognitive Virtual Machine），把目标、状态、证据、权限、终止条件从对话历史里拿出来交给运行时管理，并**对 DeepSeek V4 极度优化**。

**版本现状（2026-11-13 核查，重要）**：最新正式版已跳到 **v4.0.4（2026-11-06）**，但**公开源码一字未动**——HEAD 仍是旧报告研究过的 `2d0b22e`（2026-10-31 同步），v4.0.0–v4.0.4 五个 tag 全部指向同一个旧提交。4.0 的二进制是从作者私有 dev repo 构建的，公开仓只是滞后的同步投影。**旧报告的结论全部仍然成立**（机制都在公开代码里，代码没变），但 4.0 的新东西只能从 Release notes + 官网读行为，**抄得到设计、抄不到实现**。

**拆包证实（2026-11-13，安装包拆解，报告见 `~/workspace/tianshu-research/tianshu-4.0.4-拆包研究报告.md`）**：上面"抄不到实现"那句要修正——4.0 的新东西在安装包里，运行时 JS 只是混淆、不是加密，字符串全能读出来。共鸣星域、极限思考、XiaoSi 两件套、spawn-broker 这些机制在 `rivet-runtime/` 里都有名有姓、有函数、有协议、有数据结构（`pro/search/index.js` 的 sha256 与包内 `integrity.json` 登记值完全一致）。**只有桌面端前端仍然抄不到实现**（它嵌在 `tianshu-desktop.exe` 里，只能看到资源文件名）。另有一点要纠正：DSML、冻结前缀、CacheAdvisor、Meridian、信息素这些机制**早在公开源码 `2d0b22e` 里就有，不是 4.0 新东西**，旧报告研究过它们，拆包只是又验证了一遍（DSML 的正则、CacheAdvisor 的阶段乘数、冻结前缀的字段名都对得上）。

**对卡塞尔最有价值的不是它的功能清单，而是一整套以"前缀缓存优先"为架构级承诺的工程**：5 个真实长会话 2,001 次请求、6.45 亿 input tokens，**前缀缓存命中率 99.3–99.6%，账单 ¥880 → ¥20（省 97.7%）**。

### 3.1 天枢：核心机制清单

| 机制 | 一句话说明 |
|---|---|
| 冻结前缀 + appendixDelta | 系统提示词与工具定义在会话开始时冻结成字节稳定的前缀；一切动态内容只走增量块，绝不重写已冻结的前缀；前两条消息必须保持稳定（这是 99% 命中率的前提）；**已在公开源码，拆包复核一致**：`PromptEngine` 类字段（`frozenBase` / `frozenUserMerged` / `frozenPendingMerged` / `frozenBaseHash` sha256）、`appendixDelta` 可用环境变量 `RIVET_APPENDIX_DELTA` 关掉、冻结快照可继承（v1/v2 两种格式，hash 对不上就重建边界） |

## §4 NORMA/EVA 定位定稿

### 4.0 分工一句话

- **NORMA = 办公伙伴**：帮路专员处理文字、表格、文档、日程、信息整理这些"办公室里的活"，像一位记得所有事、会主动把活干完的副官。
- **EVA = 工程搭档**：帮路专员读代码、改代码、跑验证、管仓库这些"工程里的活"，像一位能独立施工、交付要拿证据的工程师。
- **区分标准**：NORMA 的产出是**文档和结论**，EVA 的产出是**可验证的改动**。凡是需要"改了东西、要拿测试/diff 自证"的活，一律是 EVA 的；凡是"写出来、理清楚、发出去"的活，一律是 NORMA 的。

**外部佐证**：天枢自己在 4.0 里也做了同样的二分——共鸣星域（聊天/理思路/查消息）与天枢内核（写代码）分开，官网原话是"写代码交给天枢内核，聊天、理思路、查新消息交给共鸣星域"。连最工程向的 harness 都认为需要一个独立的聊天伙伴域。NORMA/EVA 的二分不是拍脑袋，是行业里已经有人用产品验证过的分法。**NORMA 应该按"伙伴"设计（记得事、会聊天、主动提醒），而不是按"少了工具的 EVA"设计。**

### 4.1 NORMA（办公，对标 Cowork）：功能清单

| # | 功能 | 说明 |
|---|---|---|
| N1 | 文档读写与起草 | 读/写 Word（docx）、纯文本、Markdown；起草、改写、润色、缩写、翻译；保留格式与修订痕迹 |
| N2 | 表格处理 | 读/写 Excel（xlsx）：整理数据、算公式、做透视、画图表；CSV 导入导出 |
| N3 | 演示文稿 | 读/改 PPT（pptx）：按大纲生成幻灯片、换模板、提炼要点；不追求设计师级排版，追求"能直接讲" |
| N4 | PDF 阅读与提炼 | 读 PDF、提炼要点、回答针对文档的问题、做中英文摘要 |
| N5 | 联网查资料 + 整理成结论 | 联网搜索最新信息，整理成带来源的简报，而不是只给一堆链接 |
| N6 | 多步办公任务（Goal 式） | "把这周的报销单整理好""把会议纪要发给全组"这类跨多步的任务，自己拆步骤、自己跑完，中途不反复问要不要继续 |
| N7 | 日程与提醒 | 看日历、约时间、设提醒、到点主动提醒；与待办清单打通 |
| N8 | 收件箱/消息整理 | 读邮件与群消息，摘要、分类、起草回复（发之前必须经用户确认） |
| N9 | 文件整理与检索 | 在指定文件夹里找文件、按名/按内容检索、归档、重命名、去重 |
| N10 | 记忆与偏好（办公侧） | 记得用户的写作风格、常用模板、常联系的人、制度与流程（比如报销规则）；新任务自动带上约束类记忆，不劫持新任务 |
| N11 | 对话与理思路（共鸣式） | 闲聊、理乱糟糟的想法、头脑风暴、给建议；不需要动工具时不碰工具 |
| N12 | 定时/后台任务 | 每天早上 8 点出简报、每周五汇总周报；关窗口后任务按策略补跑，全局可一键叫停 |
| N13 | 模板与范文库 | 常用公文、邮件、周报、简历模板，一句话套用；用户自己的范文沉淀成模板 |
| N14 | 交付物预览与导出 | 文档/表格/幻灯片生成后给预览，确认再导出；导出的文件落盘位置明确、可回溯 |
| N15 | 主动提醒分级 | 只有"要你处理的事"（审批、截止、失败）才钉住提示；闲聊与轻提醒合并、限额、频率可调（默认适中） |

**NORMA 不该有什么（5 条硬禁）：**
- ❌ **不碰代码仓库**：不读、不改、不跑任何代码文件；用户说"帮我改这段代码"时，NORMA 应主动建议切 EVA，而不是自己硬上。
- ❌ **不跑终端命令**：没有 shell，没有 `rm`、没有 `git`、没有安装包；一切"执行"都只发生在办公软件与文件层面。
- ❌ **不做多智能体工程编排**：没有 /team、/council、/galaxy，没有分波施工，没有代码审查编队。
- ❌ **不接 MCP 代码工具与 LSP**：代码类的外部工具一律不在 NORMA 的工具表里。
- ❌ **不承诺"已验证"**：NORMA 的交付标准是"写清楚了、来源标了、预览过了"，不是"测试通过了"；绝不能把"写完了"说成"验证过了"。

| # | 功能 | 说明 |
|---|---|---|
| E1 | 读代码与讲结构 | 读仓库、讲结构、找入口、定位一处最值得改的地方；回答针对代码的问题 |

| E8 | Plan 模式 | 只调研不写实现，产出带 Mermaid 图 + TDD 步骤的计划文档，审批后再切回执行；计划存档可回看 |

| E10 | 极限思考式研究态 | 深度研究（搜索、读、比对）与写入互斥：研究占用仓库时写任务排队，只读照常；落地方案前检查工作区是否被改过，对不上就列出来 |
| E11 | LSP 与诊断回流 | 跳转定义、查找引用作为工具；改完自动把诊断喂回模型 |
| E12 | 检索：混合检索 + 影响半径 | BM25 + 向量 RRF 融合；改一个文件知道会影响哪些文件（导入图） |
| E13 | Goal 模式（工程版） | "修复所有类型错误"这类跨多轮目标，持续迭代到达成或预算耗尽；目标条显示迭代数 / 已耗时 / 预算剩余；中途不问要不要继续 |
| E14 | 失败恢复与自愈 | 工具调用协议加固（JSON 兜底 + DSML 恢复，接反代时不丢调用）；编辑失败强制先读文件；孤儿 tool_call 修复回写会话 |
| E15 | 用量与缓存面板（工程版） | 缓存命中率、上下文占比、本轮成本常驻状态栏；/debug cache 诊断命中率与碎裂原因；今日/7天/30天用量 |

**EVA 不该有什么（5 条硬禁）：**
- ❌ **不做办公文档套件**：不生成 Word/Excel/PPT、不排版、不做演示文稿美化；用户要写文档时建议切 NORMA。
- ❌ **不做闲聊与情感陪伴**：不主动闲聊、不做"理思路"式陪伴；EVA 的每一句话都应该指向任务进展或证据。
- ❌ **不碰用户的日程、邮件、群消息**：那是 NORMA 的领地；EVA 不读、不发、不代回。
- ❌ **不做定时后台办公任务**：不替用户早上出简报、不周五汇总周报；EVA 的后台只有工程任务（长构建、长测试）。
- ❌ **不承诺办公结论的正确性**：EVA 不对业务判断背书；它只对"代码改动有没有验证"负责。

### 4.3 两者共用什么、各自独有什么

### 4.4 切换时体验该怎么变（不只是换颜色）

切换是一次**工作模式切换**，不是主题切换。以下每一项都要变，只变颜色是不合格的：

| 切换维度 | 切到 NORMA 时 | 切到 EVA 时 |
|---|---|---|
| 问候语 | "路专员，早上好。今天有 3 个待办、2 封未读邮件，最近的是 14:00 的会。"（讲今天、讲待办、讲人） | "路专员，仓库 `cassell-agent-terminal` 在 `main` 分支，有 4 个未提交改动，上次 CI 通过。"（讲仓库、讲分支、讲状态） |
| 空态 / 首页重点 | 今日日程 + 待办 + 最近文档 + 一句"想写点什么 / 查点什么" | 仓库文件树 + 未提交改动 + 最近任务 + 一句"想改点什么 / 查点什么" |
| 工具栏 / 输入框附件 | 附件是文档、表格、图片、链接；输入框提示"写文档、查资料、理思路" | 附件是代码文件、终端命令；输入框提示"读代码、改代码、跑测试"；Plan/Ask/Agent 切换入口出现 |
| 默认思考强度 | **Medium**（办公任务要快、要顺，深度思考是浪费） | **High**（工程任务要深、要准，浅思考会返工）；开 ULTRACODE 时建议 XHigh/Max |
| 默认权限档位 | **auto**，但写文件默认只允许办公目录与文档类操作；对外发送（邮件/消息）一律要确认 | **auto**，但终端高危命令（rm、force push、DROP）一律弹确认；yolo 只在 EVA 里出现，NORMA 没有 yolo |
| 侧栏重点 | 项目 → 文档与任务；最近任务 → 办公任务（写文档、整理、日程） | 项目 → 仓库与分支；最近任务 → 工程任务（修复、重构、测试） |
| 状态栏 | 显示今日待办数、下一场会的时间 | 显示缓存命中率、上下文占比、本轮成本、分支名 |
| 审查 / 交付入口 | 交付入口是"预览并导出" | 交付入口是交付门（GREEN/YELLOW/RED）+ 独立审查 |
| 切换时的上下文 | 不丢会话历史，但要明确告诉用户"工具表已换，刚才的办公上下文还在，需要时可以问我"；反向亦然 | 同左 |
| 误用拦截 | 用户在 NORMA 里说"改这段代码"→ 不硬做，提示"这是工程活，切到 EVA 我帮你改"，一键切 | 用户在 EVA 里说"帮我写个周报"→ 提示"这是办公活，切到 NORMA 我帮你写"，一键切 |

**切换的铁律**：切换必须在 **300ms 内完成视觉切换 + 1 秒内完成工具表与问候切换**，不能出现"球变蓝了、工具还是 NORMA 的"中间态；切换后第一条系统消息必须说清"现在我是 EVA，能做什么、不能做什么"，不要让用户猜。

**长期方向（Anthropic 的教训）**：Anthropic 最终把"办公"收进了默认对话、只把"写代码"留作独立页签，因为用户最烦"决定任务属于哪里"。NORMA/EVA 长期应走向"一个输入框、按任务自动选边"，只在"要碰整机/跑命令"时才明确切 EVA——因为那是权限边界，不是功能边界。

### 4.5 ULTRACODE 在这个映射里的位置：EVA 的增强开关，不是第三条线

**判断：ULTRACODE 是 EVA 内部的增强开关（EVA 的"重型模式"），不是独立的第三条线。**

理由（5 条）：
1. **它没有独立的身份**：ULTRACODE 没有自己的问候、没有自己的颜色、没有自己的记忆域、没有自己的工具表——它借用 EVA 的工程上下文、工程工具和工程权限，只是把"一个人干"换成"多个人分工干"。一个没有身份的东西成不了第三条线。
2. **它的原语全是工程原语**：分波施工、文件冲突感知调度、多席位会诊、wave-gate、验证门——每一个都以"代码文件"和"测试"为前提。在 NORMA 的办公任务上，这些原语没有意义（你不会对一份周报做"按文件分波并行施工"）。一个只在 EVA 里有意义的东西，只能住在 EVA 里。
3. **二元模型是产品已经定下的心智**：用户已定"平时只有诺玛、开关才变 EVA"。加第三条线会把状态空间从 2 变成 3（NORMA / EVA / ULTRA），设置、权限、记忆、切换全部要乘以 3，用户要学的不是"一个开关"，而是"一张状态表"。天枢有 16 个星域，但它默认钉定一个、不自动切换——连 16 个域的产品都怕用户晕，卡塞尔更不该主动造第三个身份。
4. **它必须被显式 gating，而不是默认开启**：ULTRACODE 改变的是成本、延迟和行为（并行 worker、多模型调用、更多 token）。EVA 必须能处理"改一行代码"这种小活而不拉起整个编排；只有任务够大（多文件、要计划、要审查）时才值得开。开关形态天然适合这个 gating：默认关，够大才开，开的时候明说"这次会多花多少、大概要多久"。
5. **天枢的对照**：天枢的 /team、/council、/galaxy 是内核工具，不绑定任何一个星域——但卡塞尔不是天枢：卡塞尔的 NORMA/EVA 是面向用户的身份二分，不是面向模型的星域。天枢可以把编排放在内核里任取，卡塞尔必须把编排收进 EVA，否则 NORMA 的工具表会被工程能力污染，用户在 NORMA 里一点就会冒出"分波施工"这种看不懂的东西。

**落地的三条规则：**
- ULTRACODE 只在 EVA 里出现，开关放在 EVA 的工具区/设置里，NORMA 界面里**一个字都不要出现**；
- 默认关闭；开启时在输入框附近给一句诚实的成本提示（"将并行派出多个子代理，token 与耗时都会上升"），不要静默多花钱；
- 小任务自动不触发：即使开关开着，单文件小改动也不拉编排。

**唯一需要留的口子**：如果将来 NORMA 需要"多人会诊"式的长文档审阅（比如一份 50 页的报告要三个人从法务/财务/业务三个角度审），那应该做一个 NORMA 原生的"审阅会"，而不是把 ULTRACODE 借给 NORMA。两者名字、机制、产物都不同，不要共用一个开关。
